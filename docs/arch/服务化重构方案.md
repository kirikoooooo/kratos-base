# 服务化重构方案

## 目标拓扑

```text
external clients
  -> gateway (future) -> dashboard (HTTP/SSE control plane)
                     -> agent-runtime (A2A JSON-RPC / internal gRPC)
                                          -> memory (internal gRPC, phase 2)
```

`pkg/kernel` 不作为网络服务：它只存放服务名、稳定领域类型和跨服务契约。`api/` 保持为 protobuf 契约的唯一来源。

## 第一阶段（本次）

- 单二进制仍保留，避免先引入部署、发现和数据一致性风险。
- `agent-runtime` 的内部 Task 接口通过 gRPC 在 `127.0.0.1:9000` 监听，服务名为 `api.task.v1.InternalTaskService`。
- 使用 `KRATOS_INTERNAL_GRPC_ADDR` 覆盖监听地址；默认仅监听 loopback，拆分部署后必须配置 mTLS、服务发现和网络策略，不能直接绑定公网。
- Task 的 protobuf service 定义在 `api/task/v1/task.proto`；`task_grpc.pb.go` 作为 API 层 gRPC binding 与 proto 同目录维护。开发环境装好 `protoc-gen-go-grpc` 后执行 `make proto` 可重新生成该文件。
- HTTP、A2A JSON-RPC 与 `/rpc` 继续作为外部/兼容入口；gRPC 只面向内部服务，不绑定公网地址。
- Dashboard 继续是控制面：订阅 Trace/SSE，不成为第二个任务状态机。
- `app/dashboard` 已提供独立 HTTP Task facade（默认 `127.0.0.1:8001`），仅通过 `api.task.v1.InternalTaskService` gRPC 调用 Runtime。
- `app/memory` 已提供 `api.memory.v1.MemoryService/GetPromptContext`（默认 `127.0.0.1:9002`）；只读接口先行，避免与 Runtime 的会话写入、压缩产生并发写冲突。

## 后续拆分顺序

1. 已将 Runtime 的入口、Wire wiring 和默认配置迁到 `app/agent-runtime`；共享实现仍在根 `internal/`，待契约稳定后下沉为该服务私有实现。
2. 将 Dashboard 的 HTTP/SSE 与读模型搬到 `app/dashboard`；通过 gRPC 查询任务、通过事件总线订阅状态。
3. 当 runtime 多实例确实需要共享会话或向量检索时，再将 `internal/data/memory` 拆到 `app/memory`，定义 Memory gRPC API。
4. 有公网用户端和多个后端聚合需求后，再增加 `app/gateway`；它不持有 Agent Task 状态。

## 边界规则

- A2A 仍使用标准 JSON-RPC 2.0，因为它是 Agent 间互操作协议。
- 项目内部服务调用使用 gRPC；不要用 Dashboard HTTP endpoint 作为内部 RPC。
- Task 的权威状态仅在 agent-runtime；Dashboard 和 gateway 只持有投影/缓存。
