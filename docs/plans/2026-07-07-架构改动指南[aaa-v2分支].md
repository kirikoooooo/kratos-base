# Kratos 标准文件树详解

Kratos 官方提供了一个标准脚手架 [kratos-layout](https://github.com/go-kratos/kratos-layout)，这是所有 Kratos 项目的起点。下面我分三部分讲：**官方标准结构**、**各层职责**、**结合 DDD 的实战魔改**。

---

## 1. 官方标准文件树（kratos-layout）

```text
├── api/                            # API 协议定义（proto 文件）
│   └── v1/
│       ├── user.proto              # gRPC + HTTP 接口定义
│       ├── user.pb.go              # protoc-gen-go 生成
│       ├── user_grpc.pb.go         # protoc-gen-go-grpc 生成
│       └── user.pb.validate.go     # protoc-gen-validate 生成（参数校验）
│
├── cmd/                            # 程序入口
│   └── server/
│       ├── main.go                 # 主函数，组装依赖
│       └── wire.go                 # Wire 依赖注入生成
│       └── wire_gen.go             # Wire 实际生成的代码
│
├── configs/                        # 配置文件
│   └── configs.yaml                # 应用配置（数据库、Redis、服务端口等）
│
├── internal/                       # 私有业务逻辑（不对外暴露）
│   ├── server/                     # 协议服务器启动
│   │   ├── http.go                 # HTTP Server 初始化
│   │   └── grpc.go                 # gRPC Server 初始化
│   │
│   ├── service/                    # API 接口实现层（薄层）
│   │   └── user.go                 # 实现 api 中定义的接口，做 DTO 转换
│   │
│   ├── biz/                        # 业务逻辑层 ⭐
│   │   ├── biz.go                  # Provider（给 Wire 用）
│   │   ├── user.go                 # Usecase（用例）
│   │   └── greeter.go              # 示例 Usecase
│   │
│   ├── data/                       # 数据访问层
│   │   ├── data.go                 # Provider + 数据库初始化
│   │   ├── user.go                 # Repo 实现
│   │   └── ent/                    # （可选）Ent ORM 生成的代码
│   │
│   └── pkg/                        # 项目内部公共包
│       └── ...
│
├── pkg/                            # 可对外暴露的公共库
│   └── ...
│
├── openapi.yaml                    # OpenAPI 文档（自动生成）
├── go.mod
├── Makefile                        # 构建、proto 生成命令
└── README.md
```

## 2. 各层职责详解

### 📁 `api/` —— 接口契约层
- 只放 `.proto` 文件和生成的 `.pb.go`
- 定义了服务的"对外形态"（gRPC 方法、HTTP 路由、请求/响应结构）
- **不写任何业务逻辑**

### 📁 `cmd/server/` —— 程序入口
- `main.go`：启动 Wire、启动 Server、优雅退出
- `wire.go`：Wire 依赖注入的声明文件（只写 `//go:build wireinject`）
- `wire_gen.go`：Wire 自动生成的依赖组装代码

### 📁 `internal/server/` —— 协议适配层
- 初始化 HTTP/gRPC Server
- 注册中间件（鉴权、日志、限流）
- 把 `service` 层的方法注册到路由上

### 📁 `internal/service/` —— API 实现层（薄层）
```go
// internal/service/user.go
type UserService struct {
    v1.UnimplementedUserServer   // gRPC 嵌入
    uc *biz.UserUsecase          // 依赖业务层
}

func (s *UserService) GetUser(ctx, req) (*v1.GetUserReply, error) {
    user, err := s.uc.GetUser(ctx, req.Id)  // 调用 biz
    return &v1.GetUserReply{...}, nil       // DTO 转换
}
```
- **只做三件事**：参数校验、调用 Usecase、DTO 转换
- **禁止写业务规则**

### 📁 `internal/biz/` —— 业务逻辑层（核心，也是争议最大）
```go
// internal/biz/user.go
type UserRepo interface {            // ⭐ 仓储接口定义在 biz 层
    GetUser(ctx, id) (*User, error)
    Save(ctx, *User) error
}

type User struct {                    // 领域实体
    ID   int64
    Name string
}

type UserUsecase struct {             // 用例编排
    repo UserRepo
    tx   middleware.Transaction
}

func (uc *UserUsecase) GetUser(ctx, id) (*User, error) {
    return uc.repo.GetUser(ctx, id)
}
```
- 包含：**Usecase（用例）、Entity（实体）、Repo 接口、业务规则**
- 是 DDD 中 Application + Domain 的混合层

### 📁 `internal/data/` —— 数据访问层
```go
// internal/data/user.go
type userRepo struct {
    data *Data    // 数据库连接
}

func (r *userRepo) GetUser(ctx, id) (*biz.User, error) {
    // 从数据库读取，转换为 biz.User 返回
}
```
- 实现 `biz` 层定义的 Repo 接口
- 处理 ORM、缓存、外部 RPC 调用
- **不写业务规则**

## 3. 官方 Layout 的"DDD 缺口"

官方 layout 是**偏 MVC 风格**的，对 DDD 支持不够显式：

| 问题 | 表现 |
|---|---|
| `biz` 层职责模糊 | Usecase、Entity、Repo 接口全挤在一起 |
| 没有 Domain Event 的位置 | 官方没给领域事件留目录 |
| 没有 Value Object 的概念 | 所有东西都是 Entity |
| 没有 Application/Domain 的明确分离 | 容易写成"大 Usecase" |

## 5. 关键约定（避免踩坑）

### ✅ 依赖方向（必须严格遵守）
```
service → biz（Usecase） → biz（Repo 接口）
                              ↑
                          data（Repo 实现）
```
- `service` 只能调用 `biz` 的 Usecase
- `biz` 的 Usecase 只能调用 `biz` 定义的 Repo 接口
- `data` 实现 `biz` 的 Repo 接口
- **禁止反向依赖**（data 不能 import biz 的 Usecase）

### ✅ 充血实体 vs 贫血实体
```go
// ❌ 贫血：所有逻辑在 Usecase
func (uc *AgentUsecase) ExecuteStep(session, step) error {
    if session.Status != Running { return err }
    if session.TokenUsed + step.Tokens > session.MaxTokens { return err }
    session.Plan = append(session.Plan, step)
    ...
}

// ✅ 充血：逻辑在实体
func (s *AgentSession) ExecuteStep(step Step) error {
    if s.Status != Running { return err }
    if s.TokenUsed + step.Tokens > s.MaxTokens { return err }
    s.Plan = append(s.Plan, step)
    ...
}

func (uc *AgentUsecase) ExecuteStep(ctx, sessionID, step) error {
    session, _ := uc.repo.Get(ctx, sessionID)
    err := session.ExecuteStep(step)  // 调用实体方法
    uc.repo.Save(ctx, session)
    return err
}
```

### ✅ Wire 依赖注入
```go
// internal/biz/agent/wire.go
//go:build wireinject
package agent

import "github.com/google/wire"

var ProviderSet = wire.NewSet(
    NewAgentUsecase,    // Usecase
    // Repo 接口在 data 层实现，这里不注入
)
```

## 总结

| 维度 | 官方 Layout | DDD 魔改版 |
|---|---|---|
| `biz` 层 | 扁平，所有业务堆在一起 | 按限界上下文拆分子包 |
| 实体 | 贫血模型 | 充血模型（行为内聚） |
| 领域事件 | 无 | 显式定义 `event.go` |
| 依赖方向 | 基本正确 | 严格遵循依赖倒置 |
| 适用场景 | 简单 CRUD | 复杂领域（Agent Harness） |

> **官方 layout 是起点，不是终点。** 对于 Agent Harness 这种领域复杂的系统，强烈建议在 `biz` 内部按限界上下文拆分子包，并严格区分 Entity、Usecase、Repo 接口，否则很快会退化成"一个 5000 行的 `agent_usecase.go`"。
